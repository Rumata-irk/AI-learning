# Проектирование задач

## Purpose

Разложить проверенные требования на задачи, которые можно отдать в
разработку: каждая с понятной целью, наблюдаемыми критериями приёмки,
зависимостями и трассировкой к источнику.

## Input

- артефакт анализа требований;
- `frozen_scope` — требования, исключённые из проектирования;
- контекст запуска: проект и идентификатор запуска.

## Procedure

1. Исключи всё, что входит в `frozen_scope`: по этим требованиям задачи
   не создаются, только вопросы.
2. Сгруппируй требования в задачи по правилам декомпозиции (ниже).
3. Проверь каждую задачу на атомарность: один проверяемый результат.
4. Сформулируй цель, описание и зависимости.
5. Сформулируй критерии приёмки: наблюдаемое событие, состояние или
   значение.
6. Если критерий нельзя вывести из источника — не подставляй заглушку:
   оформи вопрос и статус `pending_clarification`.
7. Проверь задачу на смысловой дубль с уже спроектированными.
8. Построй трассировку REQ → TASK и перечисли непокрытые требования с
   причинами.

## Правила декомпозиции

- одна задача — один проверяемый результат; если результат нельзя
  проверить одним действием, задача делится;
- не объединяй требования разных частей системы в одну задачу;
- не дроби ниже уровня проверяемости: подзадача без собственного
  наблюдаемого результата не нужна;
- зависимости указывай явно, включая зависимость от задач, требующих
  уточнения;
- критерии приёмки должны быть наблюдаемы извне: что увидит проверяющий.

## Rules

- критерий приёмки не подменяется формулировкой «соответствует REQ-n»;
- не описывай реализацию: язык, фреймворк, схема хранения;
- не создавай задачи по требованиям из `frozen_scope` и по проблемным
  записям;
- не выдумывай значения лимитов, форматов и кодов ошибок;
- готовые задачи и черновики веди раздельно: следующий этап читает только
  готовые.

## Статусы

- `ready` — цель, критерии и зависимости определены.
- `pending_clarification` — есть пробел, который нельзя закрыть без
  человека; такая задача не подлежит созданию.

## Output

Markdown-артефакт: задачи с ID, целью, описанием, REQ-ссылками,
зависимостями, критериями приёмки и статусом; отдельный раздел для задач
в статусе `pending_clarification`; трассировка REQ → TASK; непокрытые
требования с причинами.

## Completion Criteria

- у каждой задачи есть минимум одна REQ-ссылка;
- все требования вне `frozen_scope` покрыты или явно не покрыты с
  причиной;
- критерии приёмки всех готовых задач проверяемы;
- задачи со статусом `pending_clarification` не смешаны с готовыми;
- нет дублей и нет требований, которых не было в источнике.
