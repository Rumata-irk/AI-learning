# QA Requirements Workflow

Мультиагентный проект OpenCode: анализ требований → проектирование задач и тестовой модели → проверка результатов → запись и отчёт. Четыре агента разделяют ответственность: `qa-orchestrator`, `requirement-reviewer`, `task-designer`, `test-designer`. Каждый специалист работает по своему skill.

## Быстрый запуск

Нужны Python 3.10+, OpenCode и модель с поддержкой вызовов инструментов.

```powershell
python -m pip install -r requirements.txt
opencode
```

Запустите команду `/qa-flow` или передайте запрос вручную:

> Обработай страницу healthchecker-demo в проекте DEMO. Сохрани артефакты и отчёт. Не выдумывай отсутствующие ожидания.

Изменения агентов, skills и `opencode.json` применяются после перезапуска OpenCode. Пример требований — `demo/requirements.json`, результаты — `artifacts/<run-id>/`.

## Offline demo

```powershell
python demo/run_flow.py
```

Создаёт артефакты для страницы `healthchecker-demo` со статусом `PARTIAL`. Готовые результаты и черновики разделены: следующий этап читает только `tasks` и `scenarios`, а `drafts` остаются для вопросов человеку.

## Готовые результаты и черновики

Контракт артефактов:

- `tasks.json`: `tasks` — задачи, готовые к созданию; `drafts` — задачи по замороженным требованиям с полем `frozen_by`;
- `test_model.json`: `scenarios` — готовые сценарии; `drafts` — сценарии по замороженным требованиям.

Правило: оркестратор создаёт записи только из готовых массивов. Всё, что имеет `frozen_by` или статус `pending_clarification`, не попадает во внешние системы и не передаётся дальше как готовое.

## Интеграции

`qa-local` — локальный MCP-сервер на stdio без аккаунтов. Читает демонстрационную страницу и хранит локальные задачи и тесты в `demo/store.json`; это не Jira и не Qase. Повторный вызов с тем же внешним ключом возвращает существующую запись, а при расхождении содержания — ошибку.

Для реальных систем подключите MCP-серверы Confluence, Jira и Qase в `opencode.json`, передайте секреты через переменные окружения и ограничьте операции: чтение для источника требований, запись — только для задач и тестов.

## Проверка

```powershell
python -m unittest discover -s tests -v
```

Покрыто: MCP stdio, чтение требований, идемпотентное создание, конфликт данных, разделение готовых результатов и черновиков, восстановление после частичного сбоя.

## Восстановление после частичного сбоя

Переменная `QA_LOCAL_FAIL_AFTER=N` заставляет сервер вернуть ошибку после N успешных записей. Это воспроизводит ситуацию «часть задач создана, следующая операция упала».

```powershell
$env:QA_LOCAL_FAIL_AFTER="2"
python -m unittest tests.test_recovery -v
```

Повторный запуск с тем же `QA_LOCAL_STORE` продолжает работу: существующие записи возвращаются как `created: false`, создаются только отсутствующие, дублей не появляется.
