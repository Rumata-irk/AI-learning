# QA-агент: анализ требований и тест-дизайн

Инструкция AI-агента и три Skill для работы с требованиями: от получения
требований из Confluence до задач в Jira и тестовой модели в TMS.

## Флоу

Требования из Confluence → анализ (`requirement_review`) → Quality Gate →
задачи разработки (`task_design`) и тестовая модель (`test_design`) →
запись результатов во внешние системы → сохранение артефактов каждого
этапа → итоговый отчет.

Этапы `task_design` и `test_design` независимы и запускаются только
после прохождения Quality Gate анализа.

## Состав

```
qa-requirements-agent/
├── agent_instruction.md          — инструкция агента (Role ... Escalation Rules)
├── skills/
│   ├── requirement_review.md     — анализ требований: проблемы, риски, статус готовности
│   ├── task_design.md            — проектирование задач Jira по проверенным требованиям
│   └── test_design.md            — тестовая модель: positive/negative/boundary
└── artifacts/
    └── artifact_contracts.md     — контракты артефактов с JSON-примерами
```

## Примененные правила и паттерны проектирования

- **Структура Agent Instruction** из 11 элементов: Role, Responsibility,
  Scope, Input, Workflow, Tools, Constraints, Output, Quality Gates,
  Failure Behaviour, Escalation Rules.
- **Границы ответственности** описаны явно и разведены: Scope — про
  действия, Constraints — про правила работы с данными (не выдумывать,
  не имитировать, не понижать gates).
- **Минимальная автономность**: это Workflow, а не свободно планирующий
  агент — шаги фиксированы, решения агент принимает только внутри этапов
  и при обработке ошибок.
- **Quality Gates (QG-1 ... QG-3)** между этапами с правилом
  «действие ≠ успешный результат»: следующий этап не стартует, пока
  artifact предыдущего не валидирован.
- **Self-Refine/Critic** на этапах генерации артефактов: максимум две
  итерации правок, после — остановка ветки и эскалация; циклы
  ограничены, чтобы не раздувать стоимость.
- **ReAct-цикл** на этапе записи: вызов инструмента → проверка
  фактического ответа (ключ Jira, id сценария в TMS) → только затем
  фиксация результата в artifact.
- **Artifact Contracts** между этапами (Producer/Consumer/Schema/Version/
  Validation/Error Handling), структурированный вывод (JSON) вместо
  передачи истории диалога; повторный этап создает новую версию артефакта.
- **Skills** по одному классу задач каждый — без «общего qa-skill»;
  в теле skill нет данных проекта (URL, project keys, ID), они приходят
  через контекст запуска; у каждого — версия и changelog.
- **Context Engineering**: источники разделены на постоянные (инструкция,
  skills) и динамические (требования, ответы инструментов); требования
  передаются дальше по флоу только в сжатом виде артефакта, без пересылки
  исходника на каждый этап.
- **Failure Behaviour и Escalation Rules** определены заранее:
  недоступные источники и инструменты, противоречия, `[GAP]` —
  с действиями и форматом эскалационного сообщения.

## Как использовать

Оркестратор или пользователь передает агенту контекст запуска:
`confluence_page`, `jira_project`, `tms_project` (Qase, TestRail,
Allure TestOps, TestIT), опционально `feature_scope` и путь для
артефактов. Дальше агент ведет флоу сам; при эскалации останавливает
затронутую ветку и запрашивает решение человека. Структуры артефактов
из `artifacts/artifact_contracts.md` при валидации можно прогонять
через JSON Schema.
