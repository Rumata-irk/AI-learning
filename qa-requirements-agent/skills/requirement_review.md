# Skill: requirement_review

Name: `requirement_review`
Version: 1.0
Used by: QA Requirements & Test Design Agent
Pattern: результат формируется как структурированный artifact по контракту;
качество проверяется по Completion Criteria до передачи данных дальше
по флоу.

## Purpose

Систематический анализ требований перед использованием для проектирования
задач разработки и тестовой модели: определить содержание и структуру
требований, выявить неоднозначности, противоречия, пробелы в полноте,
зависимости и риски.

Skill решает только эту задачу и не проектирует тест-кейсы и задачи.

## Input

- текст требований из Confluence (страницы передаются агентом);
- связанные бизнес-сценарии, если указаны в требованиях;
- критерии приемки, если заданы источником;
- ссылки на вложенные требования.

Skill не ищет отсутствующие входные данные за пределами полученного
контекста и не обращается к внешним источникам.

## Procedure

При анализе необходимо:

1. Разбить текст на атомарные требования и присвоить каждому ID `REQ-n`.
   Если требование сформулировано составное — разделить, сохранив
   исходные формулировки.
2. Классифицировать: функциональные требования, бизнес-правила,
   ограничения, нефункциональные требования.
3. Для каждого требования сохранить evidence — короткую цитату из
   исходного текста.
4. Определить критерии приемки там, где они заданы источником; там, где
   не заданы, зафиксировать как пробел, не выдумывать.
5. Выявить зависимости: между требованиями, от внешних систем и
   процессов.
6. Выявить и классифицировать проблемы:
   - `ambiguity` — неоднозначность (термин, условие или граница допустимых
     значений допускают более одной трактовки);
   - `conflict` — противоречие между двумя и более требованиями или
      разделами;
   - `gap` — недостающая информация (например, не задано поведение при
     ошибке, пустом значении, лимите);
   - `assumption` — утверждение источника, не подкрепленное требованием.
7. Оценить риски для последующего тестирования (тайминги, интеграции,
   данные, окружение).
8. Отметить критичность требования для проверки покрытия на этапе
   тест-дизайна.

## Rules

- не добавлять отсутствующие данные и требования;
- не выдавать предположения за подтвержденные требования;
- не изменять и не оценивать формулировки источника;
- не предлагать реализацию и решения;
- фиксировать противоречия как есть, с двумя цитатами, а не «примирять»
  их самостоятельно;
- каждую проблему связывать с REQ-n, к которому она относится.

## Output

Структурированный `requirements_analysis` (см. контракт в
`artifacts/artifact_contracts.md`), содержащий:

- выявленные требования: ID, формулировка, тип, evidence, критичность;
- бизнес-правила и ограничения с ID;
- критерии приемки из источника;
- зависимости;
- проблемы по категориям ambiguity / conflict / gap / assumption;
- риски;
- статус готовности артефакта для передачи на следующий этап
  (`ready` / `ready_partial` / `blocked` — при неразрешенных conflicts,
  блокирующих проектирование).

Результат структурирован так, чтобы следующий этап использовал его без
повторного анализа.

## Completion Criteria

Skill успешно выполнен, если:

- полнота: разобран весь переданный объем требований, а не выборочно;
- каждое требование имеет ID, тип и evidence;
- проблемы классифицированы и связаны с требованиями;
- артефакт не содержит выдуманных требований;
- формат соответствует контракту `requirements_analysis` v1;
- для conflicts проставлен блок `blocking` — влияет ли конфликт на
  проектирование задач и тестов.

## Out of Scope

- проектирование задач и тест-кейсов;
- оценка трудозатрат и сроков;
- формулирование уточняющих вопросов бизнесу — Skill фиксирует пробелы
  как есть, вопросы человеку формируются на этапе эскалации.
