# Skill: task_design

Name: `task_design`
Version: 1.1
Used by: QA Requirements & Test Design Agent
Consumes: artifact `requirements_analysis` (v1+), статус `ready` или
`ready_partial`.
Pattern: результат — структурированный artifact по контракту; проверка
на дубли через чтение Jira перед созданием задач.

## Purpose

Спроектировать задачи для команды разработки в Jira на основе
проанализированных требований. Skill отвечает за декомпозицию и
оформление постановки, но не за оценку сроков и распределение
исполнителей.

Работает только после прохождения Quality Gate анализа требований
(QG-1) и использует артефакт, а не «сырые» требования из памяти диалога.
Требования из замороженной области (`frozen_scope`) в проектирование не
входят — по ним формируются только запросы уточнения.

## Input

- artifact `requirements_analysis` — требования, бизнес-правила,
  ограничения, критерии приемки, зависимости, проблемы, замороженная
  область;
- контекст запуска: `jira_project`;
- сведения о существующих задачах проекта (чтение через Jira Tool).

Проблемные записи артефакта (ambiguity, conflict, gap) входными данными
для задач не являются: задача не проектируется по неподтвержденному.

## Procedure

1. Исключить из проектирования требования из `frozen_scope` — по ним
   формируются только запросы уточнения, задачи не создаются. Остальные
   требования проектируются независимо от наличия проблем в других
   областях.
2. Сгруппировать требования в задачи: одна задача — одна проверяемая
   единица функциональности. Не объединять в одну задачу требования,
   относящиеся к разным частям системы, и не дробить требование ниже
   уровня проверяемости.
3. Для каждой задачи сформировать поля:
   - название: глагол + объект («Реализовать ...», «Добавить ...»),
     без абстрактных формулировок;
   - цель: зачем нужна задача, из какого требования следует;
   - description: контекст и поведение, подтвержденное требованиями,
     со ссылками на цитаты;
   - критерии приемки: проверяемые пункты, каждый с REQ-ID; если
     конкретные критерии в требованиях не заданы — не подставлять вместо
     них ссылку на требование («поведение соответствует REQ-n») или иную
     общую формулировку: зафиксировать пробел, сформировать запрос
     уточнения (что считать выполненной задачей) и пометить задачу
     `pending_clarification` — в Jira такая задача не создается до
     получения ответа;
   - priority: из критичности требований артефакта;
   - dependencies: ID задач, которые должны быть выполнены раньше;
   - requirement_refs: все покрытые REQ-ID.
4. Проверить существующие задачи проекта на смысловые дубли; при
   совпадении — пометить задачу как `duplicate_of` вместо создания.
5. Для каждой задачи без конкретных критериев приемки сформировать запрос
   уточнения: REQ-ID, конкретный вопрос («какой результат считать
   выполнением задачи»), что блокирует (ID задачи). Такая задача получает
   статус `pending_clarification` и в Jira не создается.
6. Собрать артефакт `jira_tasks` и заполнить карту «требование → задача»,
   чтобы ни одно non-blocked требование не осталось без покрытия.

## Rules

- каждая задача имеет основание в требованиях, без ссылок на память
  модели;
- критерии приемки проверяемы: событие, состояние, значение; не годятся
  «работает корректно», «удобно пользоваться»;
- если конкретный критерий приемки в требованиях не задан, критерий не
  подменяется ссылкой на REQ-ID: задача помечается `pending_clarification`,
  в `clarification_requests` добавляется вопрос «что считать выполнением
  задачи», задача в Jira не создается;
- задача не содержит решения реализации (язык, фреймворк, схема БД),
  если они не заданы требованиями;
- при отсутствии в требованиях информации о приоритете — проставлять
  средний и помечать как derived;
- не создавать задачи из гипотез и проблемных записей;
- одна задача не наследует противоречивые требования.

## Output

Структурированный `jira_tasks` (контракт:
`artifacts/artifact_contracts.md`):

- список задач с полями: временный ID (`TASK-n`), summary, description,
  acceptance_criteria[], priority, dependencies[], requirement_refs[],
  status (`to_create` / `created` / `duplicate_of:<ключ>` /
  `pending_clarification`);
- покрытие требований: карта REQ-ID → TASK-ID;
- список не покрытых требований с указанием причины;
- запросы уточнения (`clarification_requests`): REQ-ID, конкретный
  вопрос, что именно он блокирует (ID задачи или область тестирования);
- отметки о дублях и источниках проверки дублей.

## Completion Criteria

- у каждой задачи есть хотя бы один REQ-ID в requirement_refs;
- все non-blocked требования либо покрыты задачей, либо явно перечислены
  как не покрытые с причиной;
- дубли проверены по существующим задачам проекта;
- критерии приемки всех задач проверяемы и связаны с REQ-ID; ни одна
  задача не содержит критерия-заглушки вида «соответствует REQ-n»;
- каждая задача без конкретных критериев приемки имеет статус
  `pending_clarification` и связана с запросом уточнения;
- формат artifact соответствует контракту `jira_tasks` v1.1;
- артефакт не содержит выдуманных требований.

## Out of Scope

- создание задач в Jira (выполняет агент после проверки QG-2);
- изменение существующих задач;
- спринт-планирование, оценка, назначение;
- описание технической реализации.
