# Skill: test_design

Name: `test_design`
Version: 1.0
Used by: QA Requirements & Test Design Agent
Consumes: artifact `requirements_analysis` (v1+), статус `ready` или
`ready_partial`.
Pattern: качество тестовой модели проверяется по критериям и улучшается —
применяется цикл Self-Refine (генерация → сверка матрицы покрытия и
правил → исправление).

## Purpose

Спроектировать тестовую модель по требованиям: positive, negative и
boundary сценарии, готовые к загрузке в выбранную TMS (Qase, TestRail,
Allure TestOps, TestIT). Skill отвечает за coverage, классы проверок и
их формулировки, не за выполнение тестов и не за их результаты.

## Input

- artifact `requirements_analysis` — требования, бизнес-правила,
  ограничения, критерии приемки, зависимости, проблемы;
- опционально `jira_tasks` для связи сценариев с задачами
  (`task_refs`);
- контекст запуска: `tms_project`;
- сведения о существующих сценариях TMS (чтение через Tool) — для
  проверки дублей.

Сценарии не проектируются по требованиям со статусом `blocked` и по
участкам с неразрешенным конфликтом: они попадают в список пропусков
с указанием ID проблемы.

## Procedure

1. Для каждого требования построить проверяемые условия из его
   доказанных формулировок: бизнес-правила, ограничения, состояния,
   переходы, вход/выход данных.
2. Применить техники тест-дизайна по ситуации:
   - классы эквивалентности и граничные значения — для чисел, дат,
     длин, лимитов, периодичности;
   - таблица решений и pairwise — при сочетании условий бизнес-правил;
   - state transition — если требования описывают состояния и переходы;
   - метод сценариев и error guessing — для пользовательских flow по
     доказанным условиям.
3. Сформировать сценарии:
   - `positive` — подтверждает требование в обычном режиме;
   - `negative` — проверяет поведение при нарушении условия, заданного
     требованием (источник данных недоступен, значение вне
     разрешенного, правило нарушено);
   - `boundary` — проверяет границы из требований: минимум, максимум,
     ровно/исключая, пустые и предельные значения, интервалы.
4. Каждый сценарий оформлять с полями: `TC-n`, title (что и при каком
   условии проверяется), precondition, steps[] (атомарные),
   expected_result (единственный проверяемый факт), type, priority,
   requirement_refs[], `task_refs[]`, automation.
5. Построить матрицу покрытия REQ → TC и закрыть все пробелы до
   прохождения gate: у каждого critical-требования минимум один positive и
   один negative; у каждого ограничения и бизнес-правила — минимум
   positive, negative и boundary.
6. Проверить дублирование проверок: два сценария с одинаковым
   expected_result и входными данными не допускаются.
7. Неинформативные формулировки (невозможность проверить) помечать
   `[GAP]` и выносить в артефакт как candidate на эскалацию.

## Rules

- каждый сценарий обязан иметь хотя бы один `requirement_refs` —
  проверки «на всякий случай» из общих знаний модели не создаем;
- ожидаемый результат проверяем и однозначен (значение, состояние,
  код, событие), не «функционирует корректно»;
- негативный сценарий допустим только если нарушение логически
  следует из требования: условие, данные или правило названы в источнике;
- запрещены сценарии, проверяющие требования, противоречия которых
  не сняты: такие области только в списке пропусков;
- один шаг — одно действие;
- не дублировать проверки между сценариями: при пересечении
  expected_result объединять или удалять один из;
- границы и лимиты из требований не «прикидывать на глаз»: брать
  цитированные значения, в противном случае ставить `[GAP]`.

## Output

Структурированный `test_model` (контракт:
`artifacts/artifact_contracts.md`):

- сценарии: `id`, `title`, `precondition`, `steps[]`,
  `expected_result`, `type (positive|negative|boundary)`, `priority`,
  `requirement_refs[]`, `task_refs[]`, `automation`;
- матрица покрытия REQ → TC (пустые ячейки допускаются только как
  `[GAP]`);
- список непокрытых areas с причиной (unresolved conflict /
  blocked requirement / gap в требованиях);
- статистика: сколько сценариев каждого типа, сколько требований
  без негативного покрытия.

## Completion Criteria

- каждый TC связан с минимум одним REQ-ID из артефакта анализа;
- каждое non-blocked требование покрыто минимум одним positive
  сценарием; требования с ограничениями и бизнес-правилами — также
  negative и boundary;
- ни один TC не проверяет то, чего не было в требованиях;
- дубли и пересечения проверок разрешены;
- `[GAP]`-помеченные условия вынесены в отчёт с формулировкой
  недостающей информации;
- формат артефакта соответствует контракту `test_model` v1.

## Out of Scope

- создание тест-ранов и прогонов, выполнение тестов;
- загрузка в TMS (делает агент после QG-3);
- изменение требований;
- написание автотестов и кода.
